## What I learned

**Keeping each feature in its own folder makes things easier to split later.**
Each domain has its own folder (`habits/`, `streaks/`, `auth/`), so the boundaries between them are clear in the file tree, not just in my head. When Assignment 2 asks me to split the app into services, each folder already maps to roughly one service.

**SQLite doesn't enforce foreign keys unless you tell it to.**
Foreign keys are off by default in SQLite. My `db.connect` runs `PRAGMA foreign_keys = ON` every time it opens a connection, so a check-in can't point to a `habit_id` that doesn't exist. Without that line, the column would just be a regular number and the database wouldn't stop bad data from getting in.

**Indexes on foreign keys don't happen automatically in SQLite.**
Some databases create indexes on foreign-key columns for you, but SQLite doesn't. The four `CREATE INDEX` statements in my schema target the columns I filter and join on most — like `idx_checkins_habit` on `checkins(habit_id)`, so looking up all check-ins for one habit doesn't scan every row. The app works without them, but it would slow down as the data grows.

**Schema setup should be safe to run more than once.**
`db.init_schema` checks `sqlite_master` for the `users` table before running `schema.sql`. If the tables already exist, it skips everything, so starting the app twice doesn't crash or wipe data. This matters for deployment: the app has to start cleanly after clone → install → start with no extra setup steps.

**Production and dev dependencies should be separate.**
`requirements.txt` has only what the app needs to run (Flask, Werkzeug). `requirements-dev.txt` pulls that in with `-r requirements.txt` and adds `pytest` and `pytest-cov`. In production, only the base file gets installed — no testing tools, smaller container, fewer things that can break.

**Tests have to match the real schema exactly.**
The `NOT NULL constraint failed: users.first_name` error happened because the test fixtures were inserting users without all the required columns. SQLite enforces NOT NULL even in test databases, so the test INSERT has to include every required field — `first_name`, `last_name`, `username`, `password_hash` — just like the real app does. Same thing with column names: the streaks service had to use `streak_length` and `achieved_on`, not something close. Always check generated code against the actual `schema.sql`.

**Jinja templates prevent code injection automatically.**
When I built the dashboard with Python f-strings, someone could type `<script>...</script>` as their name and it would run as real code in the browser. Jinja templates fix this by escaping special characters — `<` becomes `&lt;` — so user input always shows up as plain text. This is why you use templates instead of building HTML by hand.
